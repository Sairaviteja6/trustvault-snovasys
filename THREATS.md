# TrustVault — Threat Model (THREATS.md)

This document details our threat analysis for TrustVault, using the STRIDE threat modeling framework and defense-in-depth principles. For every threat, we state our mitigation, the verification mechanism (automated tests where applicable), and any accepted residual risks with our rationale.

---

## 1. The Core Guarantees & Assumptions

1. **Server-Side Authorisation Invariant**: Every request touching documents or metadata is evaluated strictly on the server by an isolated authorization middleware/service. The frontend UI is treated as completely hostile.
2. **Immediate Revocation**: Removal of access from a named user takes effect on the immediate subsequent HTTP request. No cached grants, no stale tokens, no unexpired signed URLs.
3. **Tamper-Evident Auditability**: Every access attempt (successful and refused) is permanently recorded with cryptographic hash chaining ($H_i = \text{SHA256}(H_{i-1} \parallel R_i)$).
4. **Data Isolation at Rest**: File contents are never stored on public file paths or directly accessible by raw IDs. Blobs are encrypted with AES-256-GCM using unique per-file initialization vectors (IV) and a server-held master key.

## 2. Threat Matrix

| Threat ID | Category (STRIDE) | Attack Vector & Description | Status | Mitigation Strategy | Test / Proof |
| :--- | :--- | :--- | :---: | :--- | :--- |
| **THREAT-01** | Spoofing / Tampering | **Insecure Direct Object Reference (IDOR) on Document Download**<br>Attacker guesses or enumerates GUID of another user's document (`/api/documents/{id}/download`). | **CLOSED** | Server verifies caller's authenticated user ID against `DocumentPermissions` (or ownership) on *every* request. Returns `404 Not Found` (NOT `403 Forbidden`) to prevent document existence enumeration. | `AccessControlTests.UserB_CannotDownload_UserA_Document_Returns404` |
| **THREAT-02** | Information Disclosure | **Direct Storage / Static URL Bypass**<br>Attacker discovers backend storage path (e.g. `/uploads/guid.pdf` or S3 pre-signed URL) and fetches file without hitting auth endpoints. | **CLOSED** | Files are stored outside web root with cryptographically random UUID names. Pre-signed URLs are strictly forbidden. All file transfers are streamed through ASP.NET Core streaming endpoints after DB authorization check. | `StorageTests.DirectPath_NotExposed_ViaStaticFileServer` |
| **THREAT-03** | Elevation of Privilege | **Access Post-Revocation (Stale Token / Cached Permission)**<br>User was granted READ, downloaded file, then owner revoked access. User uses active JWT or cached session to download again. | **CLOSED** | Permissions are evaluated dynamically against the database on each document request. Access tokens carry identity only, not per-document permissions. Refresh tokens have DB revocation flags. Revocation is instantaneous on the very next DB query. | `AccessControlTests.Revocation_TakesEffect_Immediately` |
| **THREAT-04** | Tampering | **Audit Trail Manipulation (Log Alteration / Deletion)**<br>An attacker or rogue insider with DB access attempts to delete or alter audit entries to cover tracks of an unauthorized view. | **CLOSED** | Each audit log entry contains a cryptographic hash of its payload plus the hash of the previous log entry (SHA-256 hash chaining). Altering any historical log invalidates the cryptographic chain. Database user account has `INSERT` and `SELECT` only on the `AuditLogs` table (no `UPDATE` or `DELETE` grants). | `AuditChainTests.TamperingWithLogEntry_BreaksHashChainVerification` |
| **THREAT-05** | Information Disclosure | **Metadata / Existence Enumeration via Status Codes**<br>Attacker sends requests for random UUIDs. If server returns `403` for existing files and `404` for non-existent ones, attacker maps out corporate document existence. | **CLOSED** | The authorization policy returns `404 Not Found` uniformly for both non-existent documents and documents the user has no permission to view. Refused access attempts are still logged to the internal audit trail with `Status = Refused`. | `AccessControlTests.UnauthorizedRequest_YieldsUniform404` |
| **THREAT-06** | Elevation of Privilege | **Administrator Document Snooping**<br>System Administrator leverages admin role to browse confidential corporate contracts or salary letters. | **CLOSED** | Principle of Least Privilege: Admin role is scoped exclusively to system metrics, user provisioning, and reviewing audit logs. Document read/download endpoints strictly enforce `OwnerId == UserId OR UserHasPermission(UserId)`. Admin role does NOT bypass this check. | `AccessControlTests.Admin_CannotDownload_PrivateUserDocument` |
| **THREAT-07** | Tampering / RCE | **Malicious File Upload (Polyglot / Path Traversal / Executable)**<br>Attacker uploads executable files masked as `.pdf` (e.g., `invoice.pdf.exe` or `../../malicious.dll`). | **CLOSED** | Uploaded filenames are stripped; files are saved strictly using server-generated UUIDs with no extension execution. File headers/magic bytes are inspected against an allowed MIME whitelist (e.g. PDF `%PDF-`, PNG `89 50 4E 47`, etc.). Maximum file size is strictly capped. | `FileUploadTests.ExecutableMaskedAsPdf_IsRejected` |
| **THREAT-08** | Elevation of Privilege | **Group / Tag Expansion Over-Permissioning**<br>Owner grants access to group "Developers". Later, user Bob is removed from Developers or should be excluded from Doc A, but still retains access due to group inheritance. | **CLOSED** | Tag/Group grants are "Expanded-on-Grant" into distinct per-user `DocumentPermission` records. The document owner can inspect the explicit list of granted individuals and revoke any individual user independently with zero side effects. | `AccessControlTests.RevokingOneUserFromGroupGrant_PreservesOtherUsers` |
| **THREAT-09** | Repudiation | **Silent Access / Unlogged Document Views**<br>A route or handler allows streaming document content before or without recording the audit log entry. | **CLOSED** | Transactional audit execution: file streaming cannot complete without dispatching the audit log record. Both successful reads and rejected attempts execute through standard ASP.NET Core Action Filters / Middleware that guarantee audit persistence. | `AuditTests.FailedAccessAttempt_IsRecordedInAuditTrail` |
| **THREAT-10** | Tampering | **Cross-Site Request Forgery (CSRF) / Token Theft**<br>Attacker steals session or tricks user into performing unintended permission grants or deletions. | **CLOSED** | JWT authentication delivered via Authorization Bearer headers (immune to browser-automatic CSRF submission). Strict CORS configuration allowing only verified frontend origin. | `SecurityHeaderTests.Cors_RejectsUnauthorizedOrigins` |
| **THREAT-11** | Injection | **SQL Injection in Search and Filters**<br>Attacker injects SQL payloads through document search query parameters (name, owner, category, date). | **CLOSED** | Entity Framework Core parameterized queries exclusively. Zero raw SQL string concatenation. | `SearchTests.SqlInjectionPayloads_AreTreatedAsLiteralStrings` |
| **THREAT-12** | Information Disclosure | **Document Content at Rest on Server Storage**<br>Physical server compromised, raw disk dump, or unauthorized local OS read of uploaded document files. | **CLOSED** | Files are encrypted at rest using AES-256-GCM. The encryption key is derived/managed separately from the file storage directory, and each document uses a distinct cryptographically random IV. | `EncryptionTests.StoredFileOnDisk_IsEncryptedAndUnreadableWithoutKey` |
| **THREAT-13** | Denial of Service | **Audit Log Flooding & Storage Exhaustion**<br>Attacker hammers endpoints with unauthorized requests to fill database storage via audit logs. | **ACCEPTED / MITIGATED** | Rate limiting applied per IP and per authenticated user using ASP.NET Core RateLimiter. However, distributed DoS from rotated IPs could still inflate logs. We accept this residual risk in v1 and mitigate with IP rate limiting and database size alert monitoring. | `RateLimiterTests.ExcessiveRequests_AreThrottled429` |
| **THREAT-14** | Information Disclosure | **Timing Attacks on Permission Verification**<br>Attacker measures API response time differences between "Document does not exist" vs "Document exists but user has no access". | **ACCEPTED (DOCUMENTED)** | Response times may differ by a few milliseconds due to DB lookup vs immediate return. In v1, database lookups are indexed on DocumentId so lookup differential is sub-millisecond, but we openly document this accepted limitation. | Monitored via benchmark logs. |

## 3. How We Verify These Defenses

Our automated test suite explicitly runs adversarial test cases corresponding directly to each threat above. 

> **Challenge Assertion**: If any authorization check in our controllers or services is removed, the corresponding `AccessControlTests` will immediately fail.
